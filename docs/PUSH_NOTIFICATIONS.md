# 管理者・主任・担当者の通知

更新日: 2026-10-03（JST）

## 利用者の操作

管理者・主任・担当者でログインすると、会場案内の下に通知設定が表示されます。設定を開き「この端末で通知を受け取る」を押して、ブラウザ・端末の通知を許可してください。登録は端末ごとで、最大5台の有効なログイン端末を登録できます。「この端末の通知を止める」で停止できます。

管理者・主任は全グループ、担当者は自分のグループの新しい確認中の注文を受け取ります。アプリを閉じた状態でも、対応ブラウザとOSの通知機能が動作していれば届きます。iPhone・iPadはiOS/iPadOS 16.4以降でホーム画面に追加し、追加したアプリから通知を許可します。[WebKitの公式説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

通知は「新しい注文があります」という固定文です。OS通知をタップすると受信履歴を開き、「注文を確認」から取りまとめに移動します。担当者は担当グループ、主任・管理者は全グループの注文を確認できます。すでにアプリが開いている場合はページを再読み込みせず、入力中のカートを維持します。注文送信中の画面切替は行いません。参加者名、グループ名、料理名、数量、金額はロック画面の通知に含めません。

## 受信履歴と未読

画面上部のベルを押すと、この端末で受け取った通知を新しい順に最新200件まで表示します。ベルの数字は未読の通知件数で、注文数とは異なります。ベルを開くだけでは既読にしません。「注文を確認」でその通知を既読にして取りまとめを開き、「すべて既読にする」で受信済みの通知をまとめて既読にできます。

受信時刻・通知識別子・既読状態・新着の件数を端末内のIndexedDB（ブラウザの保存領域）に保存し、再読み込み・同じアカウントでの再ログイン後も保持します。別の端末には同期しません。利用者・役割・所属グループが変わった場合は履歴を分離します。氏名・席名・生の利用者ID・注文内容・認証情報は保存せず、利用者の範囲と注文の照合にはSHA-256で作った識別値だけを使います。端末のサイトデータを消した場合、ブラウザがデータを消した場合は履歴も消えます。保存機能が利用できなければ画面内だけの履歴となり、保存できない旨を表示します。

初回の注文一覧取得は基準を作るだけで、過去の注文を新着として大量通知しません。一度基準を作った端末では、再読み込み後も新しく見つかった注文を記録します。画面を閉じている間のWeb PushもService Workerで受信時に記録します。本文を送らない仕組みのため、プッシュ受信直後は新着件数が不明な場合があります。次の認証済みの注文取得で件数を補い、短時間の同じ新着案内はまとめて二重表示を抑えます。実装前の通知や、この端末が受信していないプッシュの履歴は復元しません。受信履歴は注文一覧の代わりにはなりません。

管理者の「注文履歴だけを削除」は通知受信履歴・未読数も対象です。削除が成功した操作履歴に共有用の版を記録し、注文の取得と同じ応答で各端末へ伝えます。開いている端末では次の更新時、閉じている・通信できない端末では次に認証済みで接続したときに反映します。同じブラウザにある別アカウント・別役割の履歴も消し、通知登録・音と振動の設定は保持します。古い応答や同じ削除版の再受信で新しい通知を消したり、削除済みの注文を通知として復活させたりしません。機能追加前の削除記録では版を進めず、ソフトウェアの更新だけでは履歴を削除しません。

端末内の通知履歴はD1の復元では戻りません。OSの通知センターに配信済みの通知を全端末から遠隔削除する機能ではありません。通知の実受信が削除後にも発生した場合は新着として扱います。閉じている端末が削除版を受け取るまでの間に保存した通知は、次の接続時に一度リセットし、現在の新しい注文を再確認します。

## 通知音・振動・画面ロック

通知設定に「アプリを開いている間の音・振動」と「音・振動を確認」を用意しています。新着時に短い通知音と対応端末のバイブレーションを要求し、設定は利用者の範囲ごとにこの端末へ保存します。通知音はブラウザの自動再生制限があるため、画面内の操作後に有効になります。再生できない場合は確認ボタンを押してください。振動APIがない端末や許可しないブラウザでは、確認結果に利用不可と表示します。

アプリを閉じた状態や画面ロック中はWeb PushとOS通知を使用し、`silent: false`と振動パターンを指定します。ロック中の音と振動はOS・ブラウザの対応と端末側の設定に従います。Web側からiPhoneの消音・集中モード・省電力の制約を解除したり、任意の音を強制再生したりはできません。[Notifications API仕様](https://notifications.spec.whatwg.org/)、[Vibration API仕様](https://www.w3.org/TR/vibration/)

iPhone・iPadはホーム画面へ追加したアプリで通知をオンにしてください。OSの通知設定でロック画面・サウンド・バッジ等を許可します。Androidもブラウザ／追加したアプリの通知を許可し、通知設定で音・振動・ロック画面表示を確認します。Web Pushはロック画面への表示に対応しますが、通信断やOSによる停止を含む配信保証はありません。[WebKitの公式説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

通知を止めても、アプリ内の新着表示は継続します。ログアウト・session期限切れ・利用停止・一般参加者への権限変更後は新規送信対象から外れます。すでにOSへ送信済みの通知は取り消せません。再ログイン後、許可済みの端末は登録を更新します。ログイン期限は最長30日です。

通知は端末の通信・集中モード・省電力・ブラウザ設定に左右されます。タブを閉じることと、OSがブラウザのバックグラウンド動作を完全に停止することは異なります。短時間の連続注文は5秒間でまとめ、未配信の通知は最長5分で期限切れになります。注文は通知の成否にかかわらず保存されるため、運営中は「取りまとめ」の一覧も確認してください。

## 公開に必要な設定

本番公開とリモートDB・Secret変更は対象環境の承認を得てから行います。履歴削除操作を実際に実行する承認とは別です。

1. `npm run verify`を通し、stagingの架空データで確認します。
2. 対象D1の識別情報、適用済みmigration、件数を確認し、直前のTime Travel復元地点を非公開のrelease記録へ保存します。
3. `0003`まで適用済みの環境へ`0004_cleared_order_requests.sql`と`0005_push_subscriptions.sql`だけを追加します。既存データの削除、bootstrap、seedは行いません。[データ移行](DATA_MIGRATION.md)
4. 環境ごとに新規のP-256鍵ペアを生成します。秘密鍵JWKの`d`を`WEB_PUSH_PRIVATE_KEY`、非圧縮65バイト公開鍵（先頭`04`、続けて32バイトの`x`・`y`）のbase64urlを`WEB_PUSH_PUBLIC_KEY`としてWorkersへ設定します。漏えい済みの旧VAPID鍵は使用しません。両方をWorkers Secretへ一括登録できます。値をコマンド引数・履歴・console・チャット・Gitへ出さず、Git対象外の非公開ファイルまたは安全な入力から設定します。他の既存Secretは変更しません。
5. `FRONTEND_URL`が対象環境のHTTPS画面URLであることを確認し、対応Worker、対応Pagesの順で公開します。更新案内から新しいService Worker（画面を閉じていても通知を受ける処理）を有効にします。
6. 管理者・主任・担当者それぞれが端末で通知を許可し、アプリを閉じた状態・画面ロック中に別のテスト利用者から注文します。グループ制限、管理者・主任の全グループ受信、音・振動、タップ後の履歴、未読と既読の保持、ログアウト後の送信停止を実端末で確認します。本番の実注文や実通知による検証は別途承認された範囲に限定します。

未設定の場合、APIは`configured: false`を返し、画面に「プッシュ通知は準備中です」と表示します。片方だけの鍵、形式不正、HTTPSでない画面URLでも送信を有効にしません。ローカルデモには鍵を設定せず、外部送信を行いません。

## 実装と保守

WorkersのWeb Cryptoで[RFC 8292のVAPID署名](https://datatracker.ietf.org/doc/html/rfc8292)を生成します。通知本文は空で、Service Workerが固定文を表示します。外部ライブラリや別サービスの追加契約は不要です。

送信先は既知のGoogle・Mozilla・Apple・Windowsのプッシュサービスだけを許可し、redirectは追いません。404/410の失効した通知先は削除します。その他の送信失敗は注文の成功を取り消さず、情報を含まないイベント名とHTTPステータスを記録します。自動の再送キューは設けていません。

鍵を交換するときは公開鍵と秘密鍵を同時に更新します。新しい鍵と一致しない既存の端末登録は送信対象から外れます。利用者がアプリを開き直して通知をオンにすると再登録されます。コードだけのrollbackではD1全体を復元せず、新しいtableを残します。秘密情報の扱いは[境界の説明](SECRETS_AND_DATA_BOUNDARIES.md)に従います。

自動テストでは署名検証、権限・session・グループの絞り込み、登録停止、失効通知先の掃除、重複注文の通知抑止、送信失敗時の注文保存、固定通知文を確認します。外部送信はMockで置き換えています。ローカル成功は実端末・Cloudflare上の配信成功を証明しません。

2026-10-03の受信履歴・音・振動の追加はフロントエンドのみの変更です。新たなDB migration・通知鍵の生成や交換・参加者の登録変更は必要ありません。Service Workerも画面と一緒に更新する必要があります。ローカルデモでは外部プッシュを送信せず、アプリ内受信とブラウザの実保存を確認し、バックグラウンド受信処理はMockで検証します。実端末での音の聞き取り・振動・ロック中受信は公開後の検証が必要です。
