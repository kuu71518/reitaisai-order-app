# 管理者・担当者の通知

更新日: 2026-10-01（JST）

## 利用者の操作

管理者・担当者でログインすると、会場案内の下に通知設定が表示されます。設定を開き「この端末で通知を受け取る」を押して、ブラウザ・端末の通知を許可してください。登録は端末ごとで、最大5台の有効なログイン端末を登録できます。「この端末の通知を止める」で停止できます。

管理者は全グループ、担当者は自分のグループの新しい確認中の注文を受け取ります。アプリを閉じた状態でも、対応ブラウザとOSの通知機能が動作していれば届きます。iPhone・iPadはiOS/iPadOS 16.4以降でホーム画面に追加し、追加したアプリから通知を許可します。[WebKitの公式説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

通知は「新しい注文があります」という固定文です。タップすると「取りまとめ」を開きます。すでにアプリが開いている場合はページを再読み込みせず、入力中のカートを維持します。注文送信中の画面切替は行いません。参加者名、グループ名、料理名、数量、金額は通知に含めません。

通知を止めても、アプリ内の新着表示は継続します。ログアウト・session期限切れ・利用停止・一般参加者への権限変更後は新規送信対象から外れます。すでにOSへ送信済みの通知は取り消せません。再ログイン後、許可済みの端末は登録を更新します。ログイン期限は最長30日です。

通知は端末の通信・集中モード・省電力・ブラウザ設定に左右されます。タブを閉じることと、OSがブラウザのバックグラウンド動作を完全に停止することは異なります。短時間の連続注文は5秒間でまとめ、未配信の通知は最長5分で期限切れになります。注文は通知の成否にかかわらず保存されるため、運営中は「取りまとめ」の一覧も確認してください。

## 公開に必要な設定

本番公開とリモートDB・Secret変更は対象環境の承認を得てから行います。履歴削除操作を実際に実行する承認とは別です。

1. `npm run verify`を通し、stagingの架空データで確認します。
2. 対象D1の識別情報、適用済みmigration、件数を確認し、直前のTime Travel復元地点を非公開のrelease記録へ保存します。
3. `0003`まで適用済みの環境へ`0004_cleared_order_requests.sql`と`0005_push_subscriptions.sql`だけを追加します。既存データの削除、bootstrap、seedは行いません。[データ移行](DATA_MIGRATION.md)
4. 環境ごとに新規のP-256鍵ペアを生成します。秘密鍵JWKの`d`を`WEB_PUSH_PRIVATE_KEY`、非圧縮65バイト公開鍵（先頭`04`、続けて32バイトの`x`・`y`）のbase64urlを`WEB_PUSH_PUBLIC_KEY`としてWorkersへ設定します。漏えい済みの旧VAPID鍵は使用しません。両方をWorkers Secretへ一括登録できます。値をコマンド引数・履歴・console・チャット・Gitへ出さず、Git対象外の非公開ファイルまたは安全な入力から設定します。他の既存Secretは変更しません。
5. `FRONTEND_URL`が対象環境のHTTPS画面URLであることを確認し、対応Worker、対応Pagesの順で公開します。更新案内から新しいService Worker（画面を閉じていても通知を受ける処理）を有効にします。
6. 管理者・担当者それぞれが端末で通知を許可し、アプリを閉じた状態で別のテスト利用者から注文します。グループ制限、管理者の全グループ受信、タップ後の画面、ログアウト後の送信停止を実端末で確認します。本番の実注文や実通知による検証は別途承認された範囲に限定します。

未設定の場合、APIは`configured: false`を返し、画面に「プッシュ通知は準備中です」と表示します。片方だけの鍵、形式不正、HTTPSでない画面URLでも送信を有効にしません。ローカルデモには鍵を設定せず、外部送信を行いません。

## 実装と保守

WorkersのWeb Cryptoで[RFC 8292のVAPID署名](https://datatracker.ietf.org/doc/html/rfc8292)を生成します。通知本文は空で、Service Workerが固定文を表示します。外部ライブラリや別サービスの追加契約は不要です。

送信先は既知のGoogle・Mozilla・Apple・Windowsのプッシュサービスだけを許可し、redirectは追いません。404/410の失効した通知先は削除します。その他の送信失敗は注文の成功を取り消さず、情報を含まないイベント名とHTTPステータスを記録します。自動の再送キューは設けていません。

鍵を交換するときは公開鍵と秘密鍵を同時に更新します。新しい鍵と一致しない既存の端末登録は送信対象から外れます。利用者がアプリを開き直して通知をオンにすると再登録されます。コードだけのrollbackではD1全体を復元せず、新しいtableを残します。秘密情報の扱いは[境界の説明](SECRETS_AND_DATA_BOUNDARIES.md)に従います。

自動テストでは署名検証、権限・session・グループの絞り込み、登録停止、失効通知先の掃除、重複注文の通知抑止、送信失敗時の注文保存、固定通知文を確認します。外部送信はMockで置き換えています。ローカル成功は実端末・Cloudflare上の配信成功を証明しません。
